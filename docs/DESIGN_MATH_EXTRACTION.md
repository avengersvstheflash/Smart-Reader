# Design: Math Extraction (F23)

## Problem Statement

The source-side PDF viewer currently renders mathematical equations and specific symbols as missing glyphs (tofu boxes). The root cause is the presence of PDF-embedded custom fonts, specifically Type3 or CMap-encoded fonts, where the glyphs do not possess standard Unicode mappings. When the text layer is extracted by the parser, these characters are either dropped or replaced with invalid character codes.

This is a character-level extraction failure (tracked as F23) and is structurally distinct from document-level parsing failures such as chat-log misclassification (F24).

## Candidate Solutions

### (a) Math OCR via Cloud API (e.g., Mathpix candidate)

This approach involves extracting bounding boxes of unrecognized glyph clusters and transmitting them to a specialized external API for LaTeX conversion.

* **Pros:** High accuracy; handles complex multi-line equations well.
* **Cons:** Introduces a hard external API dependency, adds recurring operational costs, and increases ingestion latency. Furthermore, it complicates privacy guarantees if sensitive document data must be transmitted externally solely for OCR.

### (b) Local Math-Aware Extraction (e.g., Texify or Nougat candidates)

This requires running a specialized Vision-Language Model (VLM) locally to process regions with high densities of unmappable glyphs.

* **Pros:** No recurring external costs; keeps data strictly local, maintaining our privacy promises.
* **Cons:** Significantly increases the local bundle size (a major concern for Phase 6 Tauri packaging) and imposes high GPU/VRAM requirements on the host machine. This approach also drastically increases the baseline processing time for any document containing math.

### (c) Heuristic Symbol Substitution

This involves building a dictionary mapping known Type3 font widths and internal IDs to Unicode math symbols using localized heuristics.

* **Pros:** Very low compute overhead and zero external dependencies.
* **Cons:** Extremely fragile. This creates a high ongoing maintenance burden and will inevitably break when encountering new PDFs generated by different LaTeX compilers or varied font subsets. It is a brittle, long-term technical debt trap.

### (d) Defer and Label

Detect regions containing Type3 non-Unicode fonts and replace them with a visual placeholder indicating that the notation cannot be rendered.

* **Pros:** Low implementation effort, provides an honest failure mode, and preserves the surrounding textual integrity without hallucinating incorrect characters.
* **Cons:** Degrades the reading experience for highly technical or math-heavy papers, rendering them less actionable in the Omni reader context.

## Recommendation

Proceed with Option (d) for the v1.0 release. Given the constraints of the Pre-Tauri Product Close-Out phase, introducing a local VLM or a cloud OCR dependency carries excessive architectural risk. Providing an honest failure mode aligns with our design principles (Lens is tinted, Derivation never masquerades).

## Pipeline Impact

If Option (d) is adopted, the PDF parser must be updated to emit a distinct structural block for unmappable glyph clusters during the extraction phase. The frontend must then be extended to render a specific placeholder component (e.g., an inline pill or block alert) when this block type is encountered, allowing the user to seamlessly reference the original paper source for the exact equation.

## Effort Estimate

* **Option (a):** 3-4 sessions.
* **Option (b):** 4-5 sessions (plus Phase 6 integration overhead).
* **Option (c):** Indeterminate (high risk of failure).
* **Option (d):** 1 session.
